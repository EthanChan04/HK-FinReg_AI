# HK-FinReg AI 项目风险评估

**评估日期：** 2026-08-04  
**评估范围：** 前端依赖安全、监管语料、质量保障、构建与运行环境、生产运维、缓存安全  
**总体结论：** 当前项目核心功能、后端测试和前端构建均可通过，适合受控内测；在 P0 风险关闭、P1 风险形成可验证控制措施之前，不建议作为无人监督的生产合规决策系统使用。

## 优先级定义

| 优先级 | 定义 | 处置要求 |
|---|---|---|
| P0 | 可能直接造成安全事件、错误监管结论或关键业务不可用 | 阻断生产发布，立即处置 |
| P1 | 显著影响质量、可复现性、扩展性或生产稳定性 | 纳入近期迭代，在扩大使用范围前关闭 |
| P2 | 当前触发条件有限，但会形成长期安全或维护成本 | 纳入技术债计划并设置完成期限 |

## 风险总览

| 编号 | 优先级 | 风险 | 当前证据 | 目标状态 |
|---|---|---|---|---|
| R-01 | P0 | 前端依赖存在高危漏洞 | `npm audit`：6 high、1 low | 0 critical、0 high |
| R-02 | P0 | 监管语料与时效元数据不足 | SFC 语料为 0；证据监管机构覆盖率 77.8% | 目标场景监管机构覆盖完整，来源和有效状态可追溯 |
| R-03 | P1 | 评测集与测试层次不足 | RAG 基准仅 3 题；无前端组件测试、E2E 和覆盖率阈值 | 建立分层测试与质量发布门禁 |
| R-04 | P1 | 构建及 Python 环境不可完全复现 | Python 依赖使用宽松下限；共享环境存在版本冲突；多 lockfile 警告 | 独立、锁定、可重复安装的构建环境 |

## P0：发布阻断风险

### R-01 前端依赖存在高危漏洞

**风险描述**

当前前端使用 `next@16.2.6`，安全审计共发现 7 个漏洞，其中 6 个为 high。涉及 Next.js 权限绕过、Server Actions 拒绝服务与 SSRF，以及 PostCSS、Sharp、JS-YAML、brace-expansion、picomatch 等传递依赖问题。

**影响**

- 可能绕过中间件或代理访问控制。
- 可能造成服务端请求伪造、内部资源访问或拒绝服务。
- 当前构建虽然成功，但不能证明依赖链满足生产安全要求。

**证据**

- 依赖声明：`frontend/package.json`
- 锁定版本：`frontend/package-lock.json`
- Next.js 权限绕过：[GHSA-6gpp-xcg3-4w24](https://github.com/advisories/GHSA-6gpp-xcg3-4w24)
- Next.js SSRF：[GHSA-89xv-2m56-2m9x](https://github.com/advisories/GHSA-89xv-2m56-2m9x)

**建议措施**

1. 将 `next` 与 `eslint-config-next` 至少升级到已修复版本，优先采用当前同一 minor 的稳定版本。
2. 刷新前端 lockfile，检查 `postcss`、`sharp`、`js-yaml`、`brace-expansion` 与 `picomatch` 的实际解析版本。
3. 重新执行 lint、TypeScript、生产构建、浏览器冒烟测试和 `npm audit`。
4. 在 GitHub Actions 中加入生产依赖安全审计门禁，并配置 Dependabot 或同等依赖更新机制。

**验收标准**

- `npm audit` 显示 0 critical、0 high。
- 前端 lint、TypeScript 和生产构建全部通过。
- 代理白名单、认证转发、SSE 和主要工作区流程的回归测试通过。

### R-02 监管语料与时效元数据不足

**风险描述**

当前语料清单共 20 份文件，其中 HKMA 15 份、PCPD 3 份、SFC 2 份。AI 投顾场景的预期监管机构包括 HKMA、SFC 和 PCPD；当前评测的总体证据监管机构覆盖率为 78.0%，AI 投顾锚点仍需持续校准。20/20 文档已具备有效状态、来源 URL 和有效日期或明确元数据说明；其中两份 HKMA PDF 在本地文件完整性校验中被安全跳过，待重新采集。

**影响**

- 系统可能正确识别应涉及 SFC，却无法检索到相应证据。
- 无法可靠判断法规是否有效、已被替代或仅属于历史材料。
- 审计人员无法从引用直接回溯监管机构官方来源。
- 在财富管理、投资适当性和产品上线审查中可能产生不完整结论。

**证据**

- 语料清单：`backend/data/source_manifest.json`
- 评测基准：`backend/data/evaluation/benchmark_questions.json`
- 评测入口：`backend/app/services/evaluation/run_eval.py`
- 当前评测：`avg_evidence_regulator_coverage = 0.778`、`avg_unsupported_claim_rate = 0.1`

**建议措施**

1. 优先补齐与 AI 投顾、投资建议、适当性、产品说明和客户保障相关的 SFC 官方材料。
2. 为每份文档补齐 `source_url`、`effective_date`、`status`、`supersedes` 和 `references`。
3. 在入库阶段验证官方域名、文件哈希、发布日期和有效状态，并保留采集时间。
4. 激活知识图谱中已有但尚未充分使用的 `REFERENCES`、`SUPERSEDES` 与 `Clause` 关系。
5. 将证据侧监管机构覆盖率、官方来源完整率和有效状态完整率设为发布门禁。

**验收标准**

- 每个目标业务场景至少具备其预期监管机构的有效官方证据。
- 生产语料 `source_url`、`status` 和有效日期完整率达到 100%，或对确实不适用的字段记录明确原因。
- AI 投顾基准的证据监管机构覆盖率达到 100%。
- 对已失效或被替代文档的检索结果能够自动降级或排除，并展示替代关系。

## P1：近期必须处理的工程风险

### R-03 评测集与测试层次不足

**风险描述**

当前后端 147 个 pytest 用例和 Obligation Mapper 20 个回归用例均通过，RAG 综合基准为 53 道可审计题目。仓库仍未配置前端组件测试、浏览器端 E2E、覆盖率阈值，也没有覆盖主要 HTTP 路由和代理边界的完整自动化集成测试。大量后端测试使用 monkeypatch 或测试替身，真实模型、向量库、网络超时和 SSE 断线恢复风险覆盖有限。

**影响**

- 少量基准可能掩盖不同监管机构、语言、文档结构和问题类型下的质量退化。
- 前端交互、流式事件顺序、取消、重连和错误展示容易在改动后回归。
- 单元测试全绿不代表真实部署链路可用。

**建议措施**

1. 将基准扩展到至少 50 个可审计用例，覆盖 HKMA、SFC、PCPD、跨监管、繁体中文/英文、有效性冲突和拒答场景。
2. 引入 claim-level 检索与生成诊断指标，包括 claim recall、context precision、faithfulness、hallucination 和 noise sensitivity。
3. 增加 FastAPI HTTP 集成测试，验证认证、CORS、限流、错误响应与 SSE 事件契约。
4. 增加前端组件测试和关键用户旅程 E2E：提交分析、证据展开、Copilot、人工复核、取消和异常恢复。
5. 配置 Python、TypeScript 和前端的覆盖率报告与最低阈值。

**验收标准**

- 基准规模不少于 50 题，且按监管机构、语言和任务类型分层报告。
- 核心模块具备明确覆盖率门槛；关键 API 与前端主流程均有自动化测试。
- CI 同时阻断检索退化、引用不支持率上升和前端 E2E 回归。

### R-04 构建及 Python 环境不可完全复现

**风险描述**

后端依赖主要使用 `>=` 下限，没有项目级锁文件。当前命令行 `python` 实际来自 Hermes 自带虚拟环境，`pip check` 显示 `hermes-agent` 与 `openai` 版本冲突。仓库根目录与 `frontend/` 同时存在 lockfile，Next.js 构建因此将仓库根目录推断为前端工作区根，并输出警告。

**影响**

- 不同开发机或不同时间安装可能得到不兼容的 LangChain/OpenAI 依赖组合。
- CI 成功结果难以在生产或本地稳定复现。
- 错误的工作区根可能影响 Turbopack 缓存、文件追踪和部署产物。

**证据**

- 后端依赖：`backend/requirements.txt`
- 前端配置：`frontend/next.config.ts`
- 构建警告：检测到仓库根与 `frontend/` 两个 `package-lock.json`

**建议措施**

1. 创建项目专用 `.venv`，禁止复用其他工具的 Python 环境。
2. 采用锁定机制生成可审计的 Python 锁文件，并在 CI 使用完全一致的依赖集合。
3. 明确根目录 `package.json` 是否属于本项目；如需保留，正式配置 workspace，否则将工具依赖移出项目工作区。
4. 在 Next.js 中显式设置 Turbopack/输出追踪根目录，消除推断警告。
5. 在 CI 增加 `pip check`、干净环境安装和锁文件一致性检查。

**验收标准**

- 全新环境可通过单一文档化命令完成安装、测试和构建。
- `pip check` 无冲突。
- Next.js 构建不再报告多 lockfile 工作区根警告。
- 本地、CI 与部署环境解析出的核心依赖版本一致。

### R-05 生产限流与健康检查语义不可靠

**风险描述**

后端限流状态保存在单个 Python 进程内，并以 `request.client.host` 作为键。请求经 Next.js 服务端代理后，多个最终用户可能在后端表现为同一个代理 IP，从而共享限额；多副本部署时，各副本限额又彼此独立。健康接口固定返回 `llm_service: available`，并未验证模型、数据库、向量库或语料索引是否真正就绪。

**影响**

- 正常用户可能互相挤占限额，或攻击者可通过多副本绕过总限额。
- 健康检查可能在模型服务、数据库或索引不可用时仍返回 200。
- 自动扩缩容与流量调度可能把请求发送到未就绪实例。

**证据**

- 限流实现：`backend/app/core/rate_limit.py`
- 健康接口：`backend/app/main.py`
- 前端代理：`frontend/src/app/api/backend/[...path]/route.ts`

**建议措施**

1. 使用 Redis 或等价共享存储实现分布式限流。
2. 优先按租户、用户或 API 凭证标识限流；仅在可信代理链配置完成后使用原始客户端 IP。
3. 将 `/health/live` 与 `/health/ready` 分开：存活检查只验证进程，就绪检查验证必要依赖和索引。
4. 对外部依赖探测设置短超时、缓存和降级状态，避免健康检查放大故障。
5. 增加多用户、代理、多副本和依赖故障测试。

**验收标准**

- 多副本之间共享一致的限流计数。
- 不同租户/用户不会错误共享限额。
- 模型服务、数据库或索引不可用时，就绪检查返回非 2xx 或明确的 degraded 状态。
- 监控能够区分限流、上游故障、索引未就绪和应用异常。

## P2：计划性技术债

### R-06 Pickle 缓存存在不安全反序列化风险

**风险描述**

语料加载逻辑会从 `CORPUS_INDEX_DIR/corpus_documents.pkl` 直接调用 `pickle.load()`。Pickle 不是安全数据格式；如果缓存文件被非可信用户、进程、构建产物或共享卷篡改，反序列化可能执行任意代码。

**影响**

- 在索引目录写权限控制不严时，可能形成远程代码执行或供应链攻击路径。
- 缓存对象与 Python/依赖版本强耦合，也会降低升级兼容性。

**证据**

- 缓存加载与写入：`backend/app/services/agents/builder.py`
- 评测缓存读取：`backend/app/services/evaluation/run_eval.py`

**建议措施**

1. 优先改用 JSONL、Parquet 或其他只表示数据的安全格式。
2. 如短期必须保留 Pickle，限制目录写权限，并在读取前校验受信任签名或哈希。
3. 缓存键包含语料清单哈希、解析器版本和数据结构版本，避免加载过期对象。
4. 缓存解析失败时记录结构化告警并安全重建，不直接信任外部缓存文件。

**验收标准**

- 生产运行路径不再对可被非可信主体修改的文件执行 `pickle.load()`。
- 缓存格式具备显式 schema/version，并能检测语料或解析器变更。
- 篡改、版本不匹配和缓存损坏测试均能安全失败并重建。

## 推荐实施顺序

1. **立即：** 修复前端高危依赖并重新执行全量安全审计。
2. **立即并行：** 补齐 SFC 语料、官方来源和法规有效性元数据。
3. **近期：** 扩展 RAG 基准并将证据覆盖、引用支持与不支持声明率纳入 CI。
4. **近期：** 建立独立锁定环境，解决多 lockfile 工作区根问题。
5. **生产前：** 上线分布式、按身份限流和真实 readiness 检查。
6. **计划性：** 替换 Pickle 缓存并补充缓存完整性测试。

## 发布决策建议

- **受控内测：** 可以继续，但必须保留人工复核，且不得将输出视为最终法律或监管意见。
- **扩大试点：** 至少关闭 R-01，并为 R-02、R-03 建立可量化门禁。
- **生产发布：** 关闭全部 P0，关闭或获得正式接受的全部 P1；P2 必须有明确责任人和完成期限。
